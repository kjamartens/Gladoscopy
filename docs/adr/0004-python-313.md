# ADR 0004 — Python 3.13 as the hard-required interpreter

* **Status**: Accepted
* **Deciders**: Project maintainer (K. Martens)

## Context

`pyproject.toml` declares `requires-python = ">=3.13, <3.14"`. The
`environment.yaml` and `win_create_env.bat` boot script pin
`python=3.13` as well. The older user-facing manual had a `3.10`
reference that was already corrected (Phase 4.3 of the optimization
plan confirmed it).

A future contributor will reasonably ask "can we widen to 3.11 / 3.12
and pick up the LTS-ish window?" — hence this ADR.

## Decision

We stay on Python 3.13 (single-version pin, no fallback).

## Consequences

**Positive**

- We get the typing features (PEP 695 type aliases, `Self`, …) that
  Phase 15 plans to lean on.
- All wheels in the strict dependency pin set
  (`numpy==2.2.6`, `pandas==2.3.1`, `tensorflow==2.20.0`, …) ship
  for cp313; downgrading would force a coordinated bump of every
  pinned dep.
- One supported interpreter means we don't need a matrix in CI —
  `windows-latest + python 3.13` is the only cell.

**Negative**

- Distros / clusters that haven't moved off 3.10/3.11 yet need their
  users to install 3.13 separately. We mitigate via the
  `win_create_env.bat` one-shot.
- Some scientific Python wheels lag on the newest interpreter; if a
  pinned dep ever loses 3.13 support we have to pin around it.

## Alternatives considered

1. **`>=3.11`** — covers more distros. Reject for now: the pinned dep
   set is built for 3.13, and the typing features we want for Phase 15
   need 3.13.
2. **`>=3.12`** — narrower than option 1, same problem.
3. **Whatever-conda-ships** — leaves the version implicit; failures
   would only show at install or at runtime.

## Review trigger

Re-open this ADR when **either**:

- A pinned dependency drops cp313 support, or
- Python 3.14 (`>=3.14`) is needed by a feature we actively use.
